# Frontend implementation plan and architecture

The user's correction takes precedence over the source document's Next.js wording: this application uses React, TypeScript and Vite. The existing backend remains authoritative. Source requirements are preserved in `source-requirements.txt` as reference material.

The React application has lazy feature routes inside a shared shell. Zustand holds in-memory authentication and persisted non-sensitive theme/project/navigation preferences. TanStack Query owns server data and clears it on logout; all project queries include the project ID. Generated OpenAPI types and operation schemas are the integration contract. React Hook Form/Zod render validated operation forms, with searchable relation selectors and structured repeatable fields. No financial mutation is optimistic or automatically retried after an uncertain network result. Payment retries retain an idempotency key in memory.

Routes: `/dashboard`, `/my-work`, `/projects`, `/inventory`, `/crm`, `/customers`, `/reservations`, `/bookings`, `/bookings/new`, `/installments`, `/collections`, `/recovery`, `/dealers`, `/commissions`, `/ndcs`, `/transfers`, `/cancellations`, `/refunds`, `/possessions`, `/approvals`, `/finance`, `/documents`, `/reports`, `/users`, `/roles`, `/settings`, `/profile`, `/notifications`, `/login`, `/forgot-password`, `/reset-password`. Resource pages share permission-aware tables, action forms and detail drawers. Booking has a dedicated guided flow; reporting, documents, profile and dashboard have dedicated interfaces. Only backend-supported actions and filters are exposed.

Design: ink navy navigation, warm white canvas, cobalt actions, restrained borders, tabular financial figures, compact cards and legible tables. Light/dark/system themes share semantic tokens. Radix dialogs manage keyboard focus; mobile uses a drawer, horizontally scrollable tables, larger targets and safe-area padding. Charts are lazy-loaded and use actual backend reports. Empty portfolios show onboarding and truthful zero/empty states.

Browser authentication uses in-memory access tokens and HttpOnly refresh cookies through the same-origin proxy. Refresh calls are deduplicated within a tab and coordinated across tabs. Native adapters use the backend's explicit native endpoints. Electron keeps refresh tokens in its main process protected by safeStorage; Capacitor uses native secure storage. Packaged builds share the same UI and must be configured with a reachable HTTPS API.

Implementation sequence: foundation and authentication; shell and dashboard; resource tables/forms/details; booking and payment workflows; reports/documents/admin; native wrappers; automated tests and browser validation. Signing, store publication, physical hardware SDKs and iOS compilation on macOS require the corresponding external tools/accounts and must be documented without claiming unperformed verification.
